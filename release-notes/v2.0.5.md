# Telemetry Frame Mapper v2.0.5

v2.0.5 is a UX, accessibility and durability release. It closes the nine issues in the
[v2.0.5 milestone](https://github.com/BrandonRobare/telemetry-frame-mapper/milestone/21) and adds no
new product surface. Every issue shipped with a regression test.

Three themes: controls an operator can actually hit, destructive actions that ask first and report
failure, and a database you can get back after a bad upgrade.

## Accessibility

- Every interactive control now meets the WCAG 2.2 AA minimum target size of 24×24 CSS pixels
  (#606). The floor is applied app-wide in `index.css` and mirrored in the shared `Button`, rather
  than patched per component — roughly 78 raw `<button>` elements bypass the shared component, and a
  floor covers the ones written after this release too. On the Session Log at 1440×900 this took the
  count of undersized controls from 10 of 32 to 0 of 32; the smallest control in the app was 13×13.
- The GPS Sync offset histogram keeps its data-sized bars under a documented spacing exception —
  their width and height *are* the datum — and gains a 24×24 stepper beside the chart so the offset
  is selectable without aiming at a 4-pixel target (#606).
- Both Session Log tables scroll inside their own box. At 320 px they previously spilled onto the
  page and were clipped by the application shell, putting their delete buttons out of reach; page
  overflow at that width went from 201 px to 4 px (#606).

## Destructive actions

- Deleting a defect, a flight entry, or a splat annotation now asks for confirmation using the
  shared dialog, and each button's accessible name identifies the specific row it acts on — for
  example `Delete battery BAT-A` rather than `Delete flight entry` (#590).
- A refused delete surfaces the server's error and leaves the item on screen. Previously all three
  paths had an `onSuccess` and no `onError`: the row stayed put with no message, and the operator
  reasonably assumed the delete had worked (#590).
- Every mutation that was missing error handling now reports failures through the existing toast
  channel, including settings saves, session tags and notes, and bulk session operations (#590).

## Database durability

- The database is snapshotted immediately before startup migrations run, so a bad upgrade leaves
  something to roll back to (#680). Snapshots live in `pre-migration/` beside the database,
  retention is bounded by `backup.pre_migration_keep` (default 3, oldest evicted first), and a
  failed snapshot blocks startup rather than migrating unprotected. A fresh database, or one already
  at head, is skipped — there is no cost on a normal start.
- The restore path is documented and verified (#610). `verify_backup` re-hashes every manifest entry
  and rejects missing, resized, re-hashed, unrecorded or path-escaping files, and a round-trip test
  restores a v2.0.2 database and reaches current migration head. The procedure includes the secrets
  step that backups deliberately strip, which had never been written down.
- Fixed, found while writing that test: Alembic's `fileConfig()` ran with its default
  `disable_existing_loggers=True` inside the application's own process, so **every startup that
  upgraded an existing database silently disabled the JSONL application log for the rest of the
  process** — exactly when an operator most needs to read it.

## Correctness

- One session row with a `NULL` `folder_path` no longer returns 500 for the entire session listing.
  The column is nullable and the response model required a string, so a single legacy row made every
  other session invisible (#795).
- Removed the dead `reconstruction.presets.*.max_frames` key (#776). It was a labelled, validated,
  editable field in Settings that nothing consumed: an operator could cap a 3000-frame flight at 500,
  see the setting saved and echoed back, and watch every frame get processed anyway. The test that
  asserts every preset key reaches the trainer no longer carves out an exemption.

## Performance

- Tab modules load on demand (#594). Measured first, as the issue required: the entry chunk drops
  from 608 kB to 210 kB (gzip 173 kB → 65 kB), and the `/mobile` route from 1070 kB to 450 kB of
  decoded transfer.
- Lazy loading alone accounted for only part of that. `vite.config.ts` grouped Leaflet into a named
  chunk that the build then modulepreloaded into the entry HTML on every route, so `/mobile` and the
  share viewer — neither of which renders a map — downloaded Leaflet regardless of who imported it.
  Leaflet is now a genuine async chunk, fetched when a map-bearing tab opens.

## Progressive web app

- An installed PWA no longer pins itself to an old build (#588). Navigation is network-first and a
  successful response refreshes the cached shell, and the cache name is tied to the release version,
  so a new release installs a new worker and discards the previous shell. The cache name never
  changed before, which meant `install` was a no-op once the cache existed.
- The offline claim was removed rather than faked. The worker serves its cached shell document
  offline, but hashed JS and CSS chunks are not precached, so a cold offline launch cannot boot the
  application. `docs/USER-MANUAL.md` now says so plainly: this is a navigation fallback, not an
  offline app.

## Upgrade

- Upgrade the complete source checkout or Windows installation; `frontend-dist.zip` alone does not
  install the backend, CLI, migration, or packaging changes.
- **No new migration.** v2.0.5 adds no schema change; the last was `0016` in v2.0.4.
- New optional configuration key: `backup.pre_migration_keep` (default 3). Existing `config.yaml`
  files work unchanged.
- `reconstruction.presets.*.max_frames` is gone. An existing `config.yaml` that still carries the
  key keeps working — normal settings saves succeed — but the value is inert, and `GET /settings`
  will keep echoing it until you remove it by hand. Tracked as
  [#804](https://github.com/BrandonRobare/telemetry-frame-mapper/issues/804).
- Installed PWA clients pick up this release on their next online navigation. Because
  `skipWaiting()` is still called, a new worker takes over immediately; an update prompt that waits
  for a safe moment is deliberately not in this release.
- Before upgrading, back up the SQLite database, configuration, and required artifacts. From this
  release onward the pre-migration snapshot does that for the database automatically, but it cannot
  help with the upgrade *to* 2.0.5 — it only runs once this version is installed.
